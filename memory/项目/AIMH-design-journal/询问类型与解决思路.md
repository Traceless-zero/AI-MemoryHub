# 询问类型与解决思路（读取侧查询编排总览）

> 本文汇总 AIMH 读取侧全部询问类型。结论先行：**引擎只做确定性的检索与拒答（零-ML、BM25、CJK 二元切分、四要素加权）；理解、拆解、编排、聚合、计数等语义动作，全部在 AI 理解层。** 引擎提供原语，AI 把原语编排成答案。

---

## 一、设计原则：引擎检索，AI 聚合

- **引擎核心职责（确定性、零-ML）**：`query()`(L1 包级) / `query_anchors()`(L2 锚点级) / `resolve_query()`(消歧·拒答) / `recall_multihop()`(多跳沿 linked BFS)。全部走词法/结构化匹配，不调用任何模型。
- **AI 理解层职责（语义、可解释）**：判定询问类型、把一句多问拆成 N 个子查询、决定时间/范围硬过滤、识别并集聚合、把计数请求路由到通用函数块、把多结果合成自然语言。
- **铁律**：引擎不替用户做"理解"，AI 不替引擎做"检索"。二者经结构化返回值（列表 / `decision` 字段 / `count`）交接。

## 三、逐类详述与落点

### 类型 5 · 一句多问（multi-question）

- **定义**：单句含多个独立子问题，需分别检索再合并。
- **现状**：引擎 `query_anchors`/`resolve_query` **不拆解**，只回单一最优结果。沙箱 `orchestrate(q)` 已实现「按实体/分句拆 N → 各执行 → 按来源包分组合并」。
- **落点**：AI 理解层调用 `orchestrate`（沙箱 `to_delete/sandbox_query_orchestrator/sandbox_hma_core.py`）。**按决议不进引擎核心**，引擎只暴露原语。
- **红线备注**：合并时按来源包分组，避免把未被问到的包混入（见七·3）。

### 多跳（linked 扩散）不是独立模式

> 关键澄清（与用户敲定）：**多问题本质=把问题拆碎、多次查询、再聚合**。A+B（独立并列子问）与 A→A`（沿 linked 派生子问）**底层相同**——区别只在「子问列表怎么生成」，引擎端看到的都是「拿到 N 个子问→逐个跑→合并」。所以 `multihop` 不该是独立 mode，它只是 `multi` 下的**一种分解手法**（沿 `linked` 扩簇），由 `multihop=true` 触发，**opt-in、默认不开**。

- **全局搜索补不了关系盲区**：`query_anchors` 按关键词/锚点文本相关度捞 Top-K，看不见 `linked` 里写的「谁依赖谁、谁指向谁」。当答案恰恰藏在这条关系里——如「谁设计的拒答层，他之前还做过什么」——没有任何单篇正文同时含两者，它只在 `linked` 边（拒答层包 → author 字段 → 某人物/OC 实体包 → 该实体 `linked` 的其他包）里，关键词匹配 reconstruct 不出，只有沿 `linked` 走才到得了。
- **系统怎么执行**（hma_core.py L2913–3053）：
  1. **三路播种 seeds**：`query_anchors(q)` 锚点命中 + `query(q)` 包级单跳命中 + `_named_hit` 命名实体强制种子（查询点名的包即便 BM25 没进 top-20 也强制当种子，否则 BFS 永远到不了答案）。
  2. **BFS 扩簇**：`_linked_adjacency()`（来自 front-matter 的 `linked` 字段）从每种子扩到 `max_hops=2` 内可达包，确定性展开（sorted）。
  3. **簇内打分排序**：`score = max(包内自有锚点分 own, 直接相邻 seed 的 link-boost)`；命名实体命中 +1_000_000 强提权（破解跨包 BM25 饱和压底）；最终按 `(-score, hop, rid)` 排序，完全确定、跨 run 不漂移。
- **性质**：这是**确定性图遍历**，不是那套被否掉的「向量 graph-RAG 瞎猜边」——正是反向量哲学的红利；代价也明确：**质量受限于写入时连边的完备度**，漏链了多跳就弱。
- **何时纯噪声**：纯事实单实体问（「scope 旋钮怎么用」）全局 Top-K 已返回正确包，多跳只会把 `linked` 邻居拉进来稀释精度——所以它是 opt-in 旗标，不是默认开。模板里 `multihop` 只作为 `multi` 下的可选分解手法，不单列 mode。

### 类型 6 · 范围·时间（scope / time）

- **定义**：带时间或范围限定的查询（「3 月」「去年」「第一季度」）。
- **现状（两层）**：
  - **软加权（已进生产）**：B 修复 `parse_time_hint` 识别中文月份（「3月」「三月十日」），`_apply_field_weights` 用原始问句解析时间加权。但权重 `W_T=3` 只给 +6 分，远小于锚点文本匹配分（400+），**只偏不强制**。
  - **硬过滤（沙箱）**：`time_filter` 按 `event_date` 命中月份硬过滤，只留匹配月。
- **落点**：生产吃软加权；硬过滤留 AI 理解层（复用 `parse_time_hint` + `event_date` 字段）。
- **红线备注**：中文数字「去年四月」相对年、「三月十日」的日级粒度仍未识别（已知限制）。

### 类型 7 · 并集·聚合（union）

- **定义**：含「都/全/各自/分别/共同/所有」等聚合词，意图是合并多个实体而非消歧选一。
- **现状（已进生产）**：`_is_union_query` 识别聚合意图，`resolve_query` 在 `decision=="clarify"` 且多实体时改为 `decision=="union"`，合并多实体结果返回，不再反问用户选哪个。
- **落点**：生产 `hma_core.py` 已落（L487-494 / L1582）。
- **红线备注**：`resolve_query` 按实体归一（同前缀标题如「对话记录 · 第N轮」归一个实体），所以「20 内会 + 21 内会」属同一实体、只回 top1——真要两包都召回须走类型 5 的 `orchestrate`。

### 类型 8 · 计数（counting）

- **定义**：「多少个 X」类查询，X = 包/文档/事件/人物/地点/主题。
- **现状（沙箱已验证）**：通用函数块 `db_aggregate`（`to_delete/sandbox_query_orchestrator/db_aggregate.py`）用参数化只读 SQL 直接数，无需给引擎加任何特化原语。
- **落点**：AI 理解层把「数什么/什么条件/什么范围」填进结构化变量；建议后续暴露为 MCP 工具 `memory_aggregate`（结构化入参、非裸 SQL 透传），并保持引擎核心零改动。
- **红线备注**：见第五节专项与第七节语义边界。

### 类型 9 · 聚焦·arena（focus / scope axis）

- **定义（正交轴，非竞争类型）**：当用户与 AI 围绕一个事件主题长时间协作、记忆存取都发生在一个目录子树时，把检索**聚焦到该子树**，屏蔽其他记忆干扰、加速检索。它**不改变**询问本身的类型（精准/模糊/计数都照常），只**收窄候选集（scope）**——是叠加在类型 1–8 之上的「竞技场 / 子目录」透镜。
- **现状（生产已落）**：`scope` 旋钮已 port 进生产引擎 `hma_core.py` 的 `query()`/`query_anchors()`/`resolve_query()`（默认 `None` = 全仓，零回归），并暴露到 3 个 MCP 工具（`memory_query`/`memory_query_anchors`/`memory_resolve`）；传入 focus 目录 → `REPLACE(filepath,'\','/') LIKE '%归一绝对路径%'` 收束候选。真·聚焦 = 把 `Memory` 指向子树（独立小索引），**而非在大索引上后过滤**（后过滤法结构性脆弱：focus 内容在根索引排不到前 N）。
- **题集测试证据（聚焦 `AIMH-design-journal`）**：


  | 指标    | 全仓    | 聚焦    | 说明                                                  |
  | ----- | ----- | ----- | --------------------------------------------------- |
  | 候选包数  | 29    | 11    | 跨子树干扰 -62%                                          |
  | 聚焦命中  | —     | 10/10 | 全部零干扰、全落 focus 子树                                   |
  | 可答题   | 16/16 | 10/16 | 丢 6 条全是用户画像题 `memory/用户/`（预期盲区，逃生舱 `scope=None` 还原） |
  | 域外对抗词 | 候选 5  | 候选 5  | 离题词拆词后宽泛匹配 focus 锚点，持平（聚焦不拦离题）                      |
  | 「太阳系」 | 候选 3  | 候选 0  | 真·收窄（design-journal 全文不含）                           |
- **关键边界（最重要）**：**聚焦只管 scope，不提 precision，也不替你拒答离题问题。** 离题拒答仍归 AI 层 `allow_abstain`。域外对抗词（design-journal 全文都不含）拆词后仍宽泛匹配到 focus 锚点，候选数基本持平——聚焦**不会**自动把这类问题挡掉。
- **落点（已落）**：AI 理解层持有 focus 状态（当前 arena 目录），检索时把 `scope` 透传给引擎；`scope` 旋钮已进生产 `query()`/`query_anchors()`/`resolve_query()`（默认 `None` 零回归）+ 3 个 MCP 工具带 `scope`（详见《工具与技能总览》第六节）。
- **红线备注**：scope 语义 = 相对 memory 根或绝对路径；**勿传仓库相对 `memory/...`**（否则 `os.path.join` 拼双 `memory/` 失配）。路径须双端 `REPLACE('\','/')` 归一。

## 四、编排路由优先级（orchestrate）

当一条询问同时触发多种模式时，沙箱 `orchestrate` 的判定顺序：

```
time_filter  >  union  >  default
（时间/范围限定优先）  （含聚合词）   （单实体常规检索）
```

- `time_filter` 优先：含「都」但主意图是时间过滤（如「3 月都开了哪些会」）时，先按月份硬过滤，再在命中集内聚合。
- `union` 次之：含聚合词且无强时间限定时，按来源实体/包分组合并。
- `default` 兜底：单实体常规检索，交回 `query_anchors` + AI 合成。

> **scope 轴正交**：聚焦（类型 9）作用于以上任何一种模式之前——它先收束候选集，再交给 `time_filter` / `union` / `default` 路由。即「先圈 arena，再在 arena 内决定怎么答」。

## 五、通用计数函数块（db_aggregate）专项

> **已落产（2026-08-28）**：MCP 工具 `memory_aggregate`——unit ∈ packages/events/persons/locations/topics，filters/event_date_like/scope/return_list/top_k；非法列/算子由引擎 ValueError 拦截（MCP 以 AGG_GUARD 文本回包）。下述设计即其实现蓝本。

### 设计：结构化变量构造器（非裸 SQL 透传）

AI **只填变量**，函数块拼出安全 SQL——不给 AI 裸 `exec` 权限（防注入/误删），又比特化原语通用：

```
db_aggregate(db, unit, filters=None, scope=None, return_list=False)
  unit    : packages | events | persons | locations | topics
  filters : [{field, op, value}]   # field 走列白名单，value 走 ? 参数化
  scope   : None=全仓 / "package:<id>"=单包子树
```

### schema 实证（sandbox index.db）

`events` 表含 `person/location/topic/event_date` 真列；`person` 存 JSON `{"张总":[], "李工":[]}`（规范名即 JSON key）。`json1` 扩展可用 → 实体计数 `json_each(person)` 提 key 再 `COUNT(DISTINCT key)` 直接数。

### 七道护栏（真工程）

1. **SELECT-ONLY**：只构造 SELECT，永不拼 UPDATE/DELETE/DROP。
2. **列白名单**：AI 只能引用 `package_id/filepath/title/summary/tags/linked/pkage_created/pkage_updated/anchors/person/event_date/location/topic`，杜绝 `sqlite_master`/pragma 窥探。
3. **值参数化**：filters 的 value 一律 `?` 占位符，绝不 f-string 插值 AI/用户文本 → 注入安全。
4. **实体列走 `json_each`** 提取规范名（key），不裸解析 JSON 字符串。
5. **只读连接**：`file:<db>?mode=ro` URI 打开，物理不可写。
6. **行数上限**：`return_list` 最多返回 500 条，避免巨型 payload。
7. **范围明确**：scope 区分全仓 vs 单包子树，消除「数包还是数事件」歧义。

### 沙箱验证数据（全绿）

| 计数单元                     | 结果 | 备注                                 |
| ------------------------ | -- | ---------------------------------- |
| 包/文档总数                   | 7  | `COUNT(DISTINCT filepath)`         |
| 角色（人物）                   | 4  | 张总/李工/王经理/陈测试，`json_each(person)`  |
| 地点                       | 1  | `json_each(location)`              |
| 主题                       | 9  | `json_each(topic)`                 |
| 事件明细行                    | 7  | `COUNT(*)`                         |
| event_date 含 2026-03 的文档 | 3  | `WHERE event_date LIKE '2026-03%'` |
| 标题含 meeting 的包           | 6  | `WHERE filepath LIKE '%meeting%'`  |

> 护栏自测：非白名单列（`sqlite_master`）、非法操作符（`DROP`）均被拒。

### 语义边界

- **硬计数**：按列/实体的计数（包数、人物数、地点数、主题数、带时间过滤的文档数）函数块直接给出确定答案。
- **软计数（topic）**：「多少个会议」是 topic 而非 typed 实体，SQL 只能按 `filepath/title LIKE` 近似；精确的"会议类"仍要引擎 `query()` 大 top-K + 去重（类型 2 路径）。**函数块管硬计数，topic 软计数归 AI 层。**

## 八、双轴框架：执行轴 × 意图轴（高频意图样例）

### 8.1 两套正交坐标，不可混淆

AIMH 对「询问」有两条独立的坐标轴，常被人混为一谈：

- **执行轴（QueryEnvelope.mode）**——*引擎怎么跑*：`single`（一次查询）/ `multi`（拆碎多次查询，AI 持 `sub_queries` 清单，引擎 `orchestrate` 确定性扇出合并）/ `enumerate`（scope 内全量枚举，路由 `list_all_in_scope`）。这是引擎的确定性执行形态。
- **意图轴（semantic intent）**——*用户这句话想干啥*：精准 / 模糊 / 综合 / 核验 / **排除 / 比较 / 验证 / 因果** ……这是对自然语言语义的分类。

二者**正交**：同一意图可映射不同执行 mode（「比较 A 和 B」→ `multi`；「除了 A 还有啥」→ `enumerate`），同一 mode 可服务不同意图（「枚举 scope 内全部」既可是枚举意图、也可是排除意图的检索底座）。**把意图当执行去开新 mode，会爆出一堆 mode、引擎退化成语义理解机，直接违背 CEMA**——这正是 multihop 那次教训（详见类型 5 后「多跳不是独立模式」）的同一类错误。

### 8.2 四个高频意图样例 → 执行映射

下列意图**全部引擎零改动**，纯靠 AI 理解层把意图分解为「适当模式的信封」再合成答案。

| 意图   | 示例                | 执行映射                                                          | 引擎改动 |
| ---- | ----------------- | ------------------------------------------------------------- | ---- |
| 排除   | 「除了 A 还有其他的吗」     | `mode=enumerate`（全量枚举 scope）+ AI 合成时 **omit A**                  | 零（见 8.3 红线） |
| 比较   | 「A 和 B 比怎么样」       | `mode=multi` + `sub_queries=[A, B]` → `orchestrate` 扇出 → AI 聚合对比    | 零（已落） |
| 验证   | 「A 是不是这样」         | `mode=single(A)` → 返回锚点 AI 比对 claim；A 不在语料则 `abstain`          | 零（已落） |
| 因果   | 「为什么 A 会这样」       | `mode=single(A)` 或 `multi` 依赖链 + `multihop=True`（沿 linked 找成因）    | 零（已落） |

### 8.3 排除意图的红线：系统不做任何排除操作

> **用户敲定（关键）**：「排除 A」**不是**系统的任何减法操作——既不加引擎 `exclude` 参数，也不让 AI 对检索列表做后过滤删除。

**根因**：AIMH 内容层级是 包 → 锚点章节 → 正文，一个包/一章里经常**同时住着 A 和 B**（如「宝石」章既写「示例信物」又写其他宝石）。任何「对检索结果集做减法」的操作，无论切在：

- **包/章粒度**（为剔 A 删整章 → B 一起没）；
- **锚点粒度**（删 A 的锚点，A、B 共用上下文仍可能波及）；
- **实体粒度**（归一索引里「宝石→示例信物」这类属性盲点会让 A、B 实体纠缠，照样误伤）；

都**会误伤共置的 B**。

**正确做法**：排除是**「答案的属性」，不是「检索集的属性」**。

> 检索层把 scope 内内容**全量返回**（A、B、C 都在）→ AI 理解全部内容 → 在**合成答案时自然不提 A**。

B 从没被删——它一直在检索上下文里，只是没进最终答案。A 的「被排除」发生在**表述层**，不发生在**数据层**，误伤从根本上消失。这与 CEMA 完全自洽：引擎只做确定性返回，理解（包括「不提 A」）在 AI 层；且「不提 A」是 AI 合成最自然的事，无需任何机械删除步骤。

**与 §10 差集塌缩分清**：数学文档 §10 的「负特征差集塌缩」（「不是 X 的 Y」→ 排除 X 坍缩到单候选）**保留**——它属单问消歧（在候选集里靠否定子句锁定唯一答案），是合法的检索层否定，与「除了 A 还有啥」的枚举排除是两回事，不要混淆。

### 8.4 统一原则

意图轴全部样例（含本文 1–9 与本节 4 类）遵循同一铁律：**检索适当内容 + AI 合成对应 framing，零减法原语**。理解——包括「不提 A」——一律发生在 AI 层表述侧；引擎只做确定性返回，不理解、不删集。

### 8.5 组合空间视角：问句 = 正交轴的组合，但被架构消解而非求解

从元层看，任意询问句确实可描述为**若干正交轴张成的组合**——但须收两处精度，否则会推导出「引擎需枚举所有组合」的错误结论。

**张成的轴**（你直觉的「4 关键词 × 4 结构」精确化）：

| 轴 | 取值 | 基数 | 性质 |
| --- | --- | --- | --- |
| A · 四要素 F | person / event_date / location / topic | 每字段 present 或 absent → 2⁴=16 子集 | **常稀疏**（非总含 4 个） |
| B · 执行模式 M | single / multi / enumerate | 3 | 干净有限轴 |
| C · 意图 I | 排除/比较/验证/因果/精准/模糊/… | 开放语义集 | **非有限轴** |
| D · scope | None / 某子树 | 2 | 二元旗 |
| E · abstain | True / False | 2 | 二元旗 |
| F · multihop | True / False（仅 multi 下有意义） | 2 | multi 的子旗 |

你口中的「4 结构维度」≈ {M, I, scope, abstain}（multihop 是 multi 子旗）。

**两处必须收精度**：

1. **四要素不是「总含 4 个」，是「最多 4 个、常稀疏」**。「拒答层是哪天落地的」仅 topic=拒答层；「示例信物值多少钱」仅 topic=宝石。引擎靠 field-weight（person4>time3>loc2>topic1）**优雅处理部分缺失**——不淘汰、只调序。故非「4×4 满叉乘」，是「子集(≤16) × 意图 × 模式(3) × 旗(8)」，稀疏组合为常态。

2. **意图轴 I 非干净有限轴，不能像 M 穷举**。「排除/比较/验证/因果」是样例非闭集。严格说「组合问题」要求有限离散轴，I 开放故非纯组合；工程妙处正在此：**AI 理解层把任意开放意图「投影」到 3 个有限执行模式之一**——比较→multi、排除→enumerate、验证→single。开放轴被压缩成有限执行轴，组合爆炸在 AI 层吸收。

**结论**：问句空间确是组合空间，但它是**被架构消解的组合问题，非被引擎求解的**。整个爆炸（16 子集 × 开放意图 × 3 模式 × 8 旗）全在 AI 理解层吸收——AI 把自然语言拆成信封（填哪些四要素、选哪个 mode、带哪些旗）；引擎永远只跑 **3 个原语**（single 一次 / multi 扇出 / enumerate 全量），对「这是哪种组合」一无所知。这正是 CEMA 反复「不加 mode」的根因：加 mode 是在引擎侧枚举组合（N 种问法→N 分支），CEMA 把组合推到 AI 层、引擎保持 3 原语极小化。嵌套中文屋在此闭环——引擎是 dumb 核心，组合理解由前包裹层替它做。
