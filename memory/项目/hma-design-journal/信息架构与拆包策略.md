# 信息架构与拆包策略（模块化与路由）

> 本文档定义 HMA 记忆库的**二级信息架构**：在五个命名空间（用户/项目/原创角色/日志/其他）之下，
> 如何把"用户数据"和"项目工程"进一步按**凝聚模块**组织，让 AI 收录时按模块增补、检索时按模块命中。

## 用户数据模块划分

落点 `memory/用户/<模块>/`。默认五个凝聚模块（q-2 铁律：主语必须是**用户本人**，不进话题类目）：

| 模块 | 装什么 | 不装什么 |
|---|---|---|
| `偏好` | 稳定偏好 / 习惯 / 工具与风格选择 | 一次性临时的选择 |
| `方法论` | 可复用的工作/思考方法、"以后这么做" | 具体某次的项目决策（归项目） |
| `身份锚点` | 自我描述 / 角色定位 / 长期身份事实 | 易变的短期状态 |
| `踩坑` | 具体教训、易错点（"别踩"） | 正向方法（归方法论） |
| `事实` | 与项目无关的稳定个人事实（家住 X、用 X 设备） | 项目相关事实（归项目） |

> 模块是**默认路由指南**，不是强制分类法。AI 收录时先判内容命中哪个模块，再落点；
> 小内容可先作为同包内的不同事件 id，不必硬拆成独立包（见下「拆包触发铁律」）。

## 项目工程模块划分（README 式功能拆包）

落点 `memory/项目/<项目名>/`，**仿照一个普通项目的 README 做功能拆包**，而非按技术子系统切。一个 md 装一类职责：

- **需求清单**（`<项目名>/需求清单.md`）：项目要做什么，**显式标 `已完成` / `未完成`** 状态（类似 roadmap / backlog）。这是项目的"活待办"。
- **项目结构**（`<项目名>/项目结构.md`）：只描述目录与文件布局。**严禁把铁律 / 约定 / 架构决策等"死东西"塞进此文件**——结构就是结构。
- **开发日志**（`<项目名>/开发日志.md`）：结构化、按时间顺序的工程记录（决策、改动、踩坑经过）。
- **约定 / 铁律**（`<项目名>/约定.md`）：把"死东西"（编码铁律、协作约定、不可违反的规则）单独成文件，与结构、日志解耦。
- 其余按需：如 `架构.md` / `接口.md` / `测试.md` 等，每个 md 单一职责。

> 与"按子系统切（引擎/技能/MCP/检索）"的区别：子系统切是**实现视角**，README 式拆包是**读者视角**——
> 新人打开项目先想"要做什么（需求）、长啥样（结构）、怎么变的（日志）、啥规矩（约定）"，而非"引擎代码在哪"。

## 新建包的 front-matter 规范

AI 落库每个事件包（写 `memory/<scope>/<id>.md`）时，必须生成如下 front-matter。引擎（`python -m hma.cli --root memory/<scope> write ...` 或 `Memory(root).write(...)`）据此落索引；`.md` 是唯一权威，索引可由 front-matter 重建。

**必填 / 常用字段：**

| 字段 | 规则 |
|---|---|
| `id` | 包内唯一（建议全局唯一）；kebab-case：小写、保留中文与字母数字，其余折叠为 `-`。建议 `<scope>-<短主题>` 或纯 `<主题>`。 |
| `title` | 可读标题，L1 检索展示用。 |
| `summary` | 一句话摘要，**≤30 字**，L1 检索展示用。 |
| `tags` | 2–5 个关键词列表 `[ a, b ]`，参与 L1 标签召回。 |
| `aliases` | 可选，同义词 / 别名列表，扩大召回。 |
| `linked` | 可选，关联包 id 列表 `[ 包id ]`，建立双向关联。 |

**不要手填的字段（引擎托管）：**

- `anchors`：由正文 `##` 二级标题决定，引擎在 derive / install / build 流程中据此自动生成，驱动 L2 `query_anchors` 细粒度召回。AI 只需把正文用清晰、有意义的 `##` 标题分章，**一般不用手填**；若直接走 `write` 且希望立即拥有 L2 锚点，可手填 `anchors: [{title, summary, tags, locator}, …]`（与 `##` 标题一一对应）。
- `created` / `updated`：引擎在首次 write 时写 `created`、每次 write 刷新 `updated`，**AI 不要手填**。

**正文约定：** front-matter 之后、`---` 之下，正文**以 `# 标题` 开头**；二级 `##` 标题即子事件锚点。

最小模板：

```markdown
---
id: <kebab-case-包内唯一>
title: <可读标题>
summary: <一句话摘要（≤30字）>
aliases: [ <别名1>, <别名2> ]
tags: [ <a>, <b>, <c> ]
linked: [ <关联包id> ]
---

# <标题>

<正文…用 ## 作为子事件锚点，供 L2 检索>
```

## 日志/（daylog）：仅闲话 + 大事件简介 + 关联

`日志/` 命名空间（daylog）的定位**严格限定**为：

- **闲话**：碎片化、非结构的日常碎念；
- **大事件简介 + 关联**：某大事件一句话简介，并 `linked` 到对应的**结构化项目包**（需求 / 日志 / 约定）。

**不做**：结构化项目跟踪（需求状态、决策记录）不属于 daylog——那些进 `项目/<项目>/` 的对应包。
daylog 是"轻量叙事索引层"，靠 `linked` 把碎片挂到正经包上，自己不承载真相。

## 拆包触发铁律：凝聚性+体积

对应设计原则③「活文档整合 / 无限拆分」——**拆包触发条件是体积 / 凝聚性，不是作者写法运气**。

- **不提前拆小东西**（CEMA 原话）：小内容硬拆成独立包 = 索引碎片化、检索噪音、维护成本上升。
- 所以本策略的"模块分类"定位是：**帮 AI 快速落点的默认路由指南**，而非"必须先建好所有空模块"。
- 过度拆分的信号：一个包只有一两句、或模块间高频互链成网状——此时应合并或升级为更高阶包。

## AI 收录时的模块路由判定

落点决策（配合 `hma-ingest` 步骤 2 的"一次比对 index"）：

1. **判命名空间**：用户 / 项目 / 其他 / OC / 日志。
2. **判模块**：内容语义命中哪个默认模块？（用户→五模块；项目→README 式功能模块：需求清单/项目结构/开发日志/约定）
3. **比对 index**：该模块包是否已存在？
   - **存在且同物** → **增补 / 覆盖该包**（update 同包，不新建）。
   - **存在但过大**（体积触发） → 在该模块下拆子包 / 子事件 id。
   - **不存在** → 仅当凝聚性确实成立，按「嵌套逻辑关系」新建模块包。
4. **严禁**：把不同模块内容塞进一个包；为小内容预建一堆空模块包。

> 此规则已写入 `hma-ingest` 技能「模块路由」段（双副本同步），AI 收录时实际执行。
